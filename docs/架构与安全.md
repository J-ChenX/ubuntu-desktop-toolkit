# 当前架构、性能与安全边界（v8）

## 语言决策

以性能和风险控制为首要目标，自有原生核心采用 **Rust**，不再以迁移成本或 ROI 为主要否决依据。v8 已落地 Rust 管理入口和 Rust 框选计算核心。不是将第三方 Nautilus、GTK、Terminator 和搜狗全部重写；也没有声称整个桌面进程已经内存安全。

| 层 | 当前实现 | 边界与作用 |
|---|---|---|
| 统一入口 desktopctl | Rust，禁止 unsafe | 命令分派、组件清单读取、流式 SHA256 校验、参数化子进程调用；无后台服务 |
| 框选纯计算 | Rust | 不持有 GTK 指针、不在计算期间分配、不回调 C、不保留调用者指针 |
| GTK 适配层 | C | 持有 GTK 对象引用、维护几何缓存、只在主线程调用 GTK、按帧调度和清理生命周期 |
| 安装与配置适配 | Python | 继续对接 APT、GSettings、用户备份；配置原子替换、fsync、不变文件跳过；不是性能热路径 |
| 第三方应用 | 原软件实现 | 保留 GNOME/GTK、Terminator、搜狗的升级与运行边界 |

C++ 也能达到很高性能，但 RAII、智能指针并不默认排除所有越界、悬空引用和数据竞争。因此没有为安全目标新增 C++ 核心。Rust 的优势是把纯计算与管理代码纳入编译期约束；C/GTK 适配边界仍需测试和审查。

参考：[Rust FFI](https://doc.rust-lang.org/nomicon/ffi.html)、[Rust panic/ABI](https://doc.rust-lang.org/reference/panic.html)、[C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)。

## 已实施性能改动

- 一次手势缓存矩形与初始选择；普通指针移动不再获取全部子控件列表和文件模型。
- Rust 计算使用连续 POD 数组和调用者提供的输出缓冲区，计算热路径不分配内存。
- 选择位图对比后，仅对变化项目调用 GTK；不变项不触发 GTK 状态写入。
- 鼠标更新合并到帧回调。释放鼠标前刷新待处理坐标，Escape 恢复逻辑不会被尚未执行的帧覆盖。
- 目录变化、尺寸变化和外部选择变化使缓存失效；缓存持有 GTK 引用，结束或销毁时释放。
- 统一管理入口按需运行，状态查询不扫描整个字体与输入法安装包；完整校验由 check 执行。
- 已清理上一轮隔离测试残留进程，并为测试运行器增加按私有 XDG_RUNTIME_DIR 精确匹配的退出清理。

## 测量结果

同机、Xvfb、5000 个空文本文件、1000×700 窗口，等待加载稳定后，600 次鼠标更新，每次请求间隔 1 ms，再等待 2 秒处理队列。实际事件间隔还包含 xdotool 进程调用开销。两组按 v7→v8、v8→v7 顺序运行：

| 版本 | 第一次 CPU 时间 | 第二次 CPU 时间 | 平均 |
|---|---:|---:|---:|
| v7 | 2.40 秒 | 2.53 秒 | 2.465 秒 |
| v8 | 2.07 秒 | 2.23 秒 | 2.150 秒 |

该场景平均 CPU 工作量减少约 **12.8%**。PSS 在这些运行中都约 170 MiB，没有足够证据宣称降低了整机或应用内存。120 次普通频率轨迹约从 1.61 秒到 1.54 秒，差异较小，不当作显著改善承诺。两次重复不足以建立严格统计置信区间，数据不代表所有文件类型、主题和显示环境，也不是输入到显示的 P99 延迟。

相同矩形算法的微基准中，C++ 约 58–61 ms，Rust FFI 约 61–65 ms（各 2 万次 × 5000 个矩形，4 轮）。Rust 包含 ABI 参数检查和 panic 边界，C++ 比较实现未包含同等防护；该结果不能作为严格同安全条件语言排名，但明确说明不能假设 Rust 一定更快。当前选择 Rust 的依据是安全约束和可接受的性能，而不是声称语言本身带来上述 12.8%。

一次约 205 个样本的 perf 采样中，GTK 约 46%、GObject 约 18%、Cairo 约 12%、GLib 约 10%。样本较少，栈展开也不完整，只用于定位方向；不能据此推算某个 Rust 函数的精确占比。采样进程停止等待超时，目标退出后完成记录，原始交互基准采用未启用 perf 的独立运行。

原始结果统一位于 `reports/performance/`；v7 数据仅作为比较基线保留。

## 安全保障及限制

- 管理器自有代码使用 `#![forbid(unsafe_code)]`，这不等于其第三方依赖也完全没有 unsafe；不拼接 shell 命令执行；核验文件路径不得越出工具包根目录。
- Rust 核心纯算法使用安全切片；唯一 unsafe ABI 适配集中在一个函数，校验空指针、对齐、长度上限、地址加法和缓冲区重叠。
- ABI 无跨语言对象所有权转移。C 负责确保内存实际有效且只在 GTK 主线程访问；这些指针有效性条件不能由 Rust 自动证明。
- 不允许 panic 穿过 C ABI；使用 catch_unwind 返回失败。进程中止和 OOM 不是它能恢复的错误。
- 矩形 ABI 有尺寸静态断言；非法参数测试、全模式矩形边界测试通过。核心和管理器 Clippy 均以 warnings-as-errors 检查通过。
- v8 包装后的 15 项交互及 10 项拖放检查通过；C 适配层在 ASan/UBSan 下通过快速释放、目录变化/窗口缩放、关闭活动手势、自动滚动、剪切粘贴撤销检查。
- ASan 测试关闭了 leak detection，Rust 静态库未做 sanitizer 插桩，且未进行长期 soak test；因此不能宣称所有内存问题已被排除。窗口或模型改变可取消原手势，测试在这种情况下验证存活与有效选择，不保证跨重载恢复旧选区。
- SHA256 清单用于完整性校验，不是可信签名。工具包本身与 sudo 授权仍是信任边界。
- 发布验证记录显示 v8 三机安装文件一致；当前运行状态以 status 为准。更新后保存工作并注销重登，确保切换桌面进程。

## 开发源与构建

- `src/desktopctl/`：Rust 管理器，Cargo.lock 与 vendor 依赖已收录。
- `src/selection-core/`：无第三方依赖的 Rust 几何核心、C ABI 头文件和测试。
- `src/nautilus-patches/`：GTK 适配改动补丁。
- `modules/file-manager/release/source/`：完整 Nautilus v8 发布源码快照。
- `src/gtk3-chooser/`、`src/gtk4-chooser/`：弹窗模块源码与构建脚本。

发布二进制使用 Rust 1.98.1 构建。普通安装不需要 Rust 编译器。重新构建管理器可运行 `scripts/build-native.sh`（要求该工具链已安装，不自动下载安装）。Nautilus 源码的 Debian Build-Depends 增加 rustc ≥ 1.82；Ubuntu 22.04 自带 Rust 包版本可能不足，维护构建应使用已固定工具链。此次构建用显式 PATH 指向 1.98.1，因它由 rustup 管理而不在 dpkg 中，使用了 dpkg-buildpackage -d；其余开发依赖已具备。v8 未重复全套上游 Tracker 测试，验收范围以这里列出的检查为准。
